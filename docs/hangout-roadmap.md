## Running it

- Postgres for every gate (ADR-0014): every play's shell needs `DATABASE_URL` and a running Postgres, including lead-PR and review gates and `sdlc baseline`, because `[app] setup` runs before every gate and fails at once without them. Locally, start Postgres 16 on port 5433 and check it is still up before each run (an idle cloud container stops it). Point `DATABASE_URL` at a scratch database of your own, for example `postgres://postgres:postgres@127.0.0.1:5433/hp_local` (create it once), never at the `postgres` maintenance database: test commands run outside a gate (an agent's own `vitest run`) migrate and truncate whatever `DATABASE_URL` names, and two parallel runs need different scratch databases. Inside a gate that database only names the server: setup creates `hp_run_` plus `SDLC_RUN_ID` (lower-cased, other characters as `_`, for example `hp_run_123_456`) through the maintenance database and drops it afterwards, so the role must be able to create databases. A gate killed before teardown leaves one behind: drop it by hand with `DROP DATABASE hp_run_... WITH (FORCE)`.
- Full history first: kit v4.0.0 fails every gate (`history` check) and refuses `gate pr` and `trace` in a shallow clone, and `sdlc status/next/run` offer merged tickets as ready there. Cloud sandboxes clone shallow: run `git fetch --unshallow` once per sandbox before any `sdlc` command.
- Ports: `app.port = "auto"` (ADR-0013, kit v5.1.0) gives smoke a free port for each run, which every gate command sees as `SDLC_APP_PORT` (also the app's `PORT`, `{port}` and `{base_url}`). Setting `SDLC_APP_PORT` to a number still overrides it. Inside a gate, `[app] setup` picks `HP_E2E_APP_PORT` and `HP_E2E_GOOGLE_STUB_PORT` for each run, locally and in CI (ADR-0014); outside a gate they still default to 3124 and 3125 (ADR-0012). `FE_BUILDER_PORT` overrides `fe-builder`'s 3210 and stays manual.
- Parallel full gates (ADR-0012, ADR-0014): each extra run gets its own checkout. The gate gives each run its own database and ports. For a run beside the main checkout:
  1. `git worktree add ../hp-<id> build/<id>` (or `main`), `git submodule update --init` in it, then `npm ci` there. Do not symlink `node_modules`: Turbopack failed to build such a worktree in this pilot (T-001-68).
  2. Point `DATABASE_URL` at a scratch database no other run uses (for the agents' own test runs outside the gate), and if the run uses `fe-builder`, set a `FE_BUILDER_PORT` no other run uses. Inside the gate, smoke, the database and the browser-test ports are picked per run (ADR-0013, ADR-0014).
  3. Run `sdlc run ...` from that checkout. Two runs in one checkout still conflict (they share `.next`).
- The runner drives every ticket play. Four agents are configured in `sdlc.toml`, all headless `claude -p`: `builder`, `fe-builder`, `tester` and `reviewer`. `fe-builder` is `builder` plus Next.js's built-in MCP server: `ops/agent-fe-builder.sh` starts `next dev` on 127.0.0.1:3210 for the run (with the agent variables cleared, so it does not write its block into `AGENTS.md`) and stops it on exit. It writes the agent's full transcript (every tool call and result) to `.sdlc-run/logs/fe-builder-<time>-<pid>.jsonl`; the runner's agent log gets the final message and one `fe-builder: denied` line per refused tool call. Its `get_errors` needs a browser session, so it reports nothing in a headless run; `get_routes`, `get_logs`, `get_compilation_issues` and `compile_route` work. Each run is a fresh process with no prior context. Permissions are file tools, the kit CLI, the test commands, and read-only git; the builder and tester also get the type-check commands. The reviewer has no Edit tool, but keeps Write for its review record. There are no MCP servers except `fe-builder`'s Next.js one, and no git writes. Pick models with `SDLC_BUILD_MODEL`, `SDLC_TEST_MODEL` and `SDLC_REVIEW_MODEL`, and give the reviewer a different model from the builder. Per ticket:
  1. First run `sdlc plan <id>` (kit v5.2.0, kit ADR-0006; adopted by ADR-0016): it prints the ticket's lane, each play's checks and write set, and the proof each AC owes. Then `sdlc run build <id> --agent builder`. The runner branches `build/<id>`, runs the agent, gates each attempt (up to `[gate] max_attempts`), feeds failures back, and commits with the `Sdlc-*` trailers.
  2. `sdlc run test <id> --agent tester`, on the same branch. Skip it for `type: test` tickets (`sdlc run test` refuses them) and for the mechanical and refactor lanes (`gate test` refuses those), and since v4.0.0 they owe no separate real-stack proof (their AC still need a passing tagged test in some suite).
  3. `sdlc run review <id> --agent reviewer --extra .sdlc-run/review-extra.md`. `--extra` takes a **file path**, not text; a sentence crashes the runner. The file says: set `reviewer: reviewer` in the record and write no model name (T-001-34's reviewer wrote its model id there). Since kit v3.2.1 the review skill exempts `test: none`, `type: test`, spike and mechanical builds from test evidence; before it, T-001-35's reviewer asked for evidence the kit refuses to produce. The kit refuses a reviewer with build or test commits on the branch. Publish its record with `sdlc review publish <id> --pr <n>`, or post `.sdlc-run/review-<id>.md` unchanged.
  4. Open the PR. CI runs `gate ci` and `gate pr`.
  5. The lead approves in chat with "approve #<n>"; the lead's agent posts the `role: lead` record on the head the lead saw, naming the instruction (who, when, PR, commit). A new head needs a new approval.
  6. Merge with a merge commit once CI and `sdlc/approval` are green and CodeRabbit has finished. Never squash: derived status reads `Sdlc-Ticket` from the commits on main.
  - Check a set-up without running an agent: `sdlc run build <id> --agent builder --dry-run` prints the branch and the exact command.
  - By hand, if the runner can't be used: commit with `sdlc commit <id> --agent <name> --play <play> -m "..."` and run `sdlc gate <play> <id>` on the clean commit. Evidence from a dirty tree records the base commit as proven.
- Lead PRs (no ticket): `sdlc prompt review --pr <n>` writes the review prompt to `.sdlc-run/prompts/review-pr-<n>.md`. A fresh `claude -p` process with the reviewer's tools runs it and writes `.sdlc-run/lead-review-<n>.md`. The author publishes it with `sdlc review publish --pr <n>`, or posts it unchanged. The `role: lead` record is posted as in step 5 above: only on the lead's "approve #<n>" for that head. `sdlc/approval` is judged by the kit pinned on the base branch.
- Never commit a `sdlc baseline --prune` result without reading it. If a check errors in that run (for example `ac-coverage`: "no test command wrote JUnit"), prune drops all of that check's entries.
- Ticket authoring (T-001-57): a ticket that touches `drizzle/**` (`lanes.strict_paths`) runs in the strict lane, so its PR needs a lead approval even when the ticket says `risk: low`. In a non-test ticket the build play cannot write `e2e/`; list those files anyway, and give the test play the `e2e/` edits in its `--extra` file.
- `type: test` tickets for shipped tickets (T-001-86..90): the build notes list every clause of each shipped AC, and the lead checks each test against the full AC text before review; a missing clause goes back to `sdlc run build` with notes, never a lead edit to the test. Once the previous such ticket merges, merge `origin/main` into the branch, run `sdlc baseline --prune --base origin/main`, read its output, and commit it with `sdlc commit <id> --agent lead --play build -m "..."`. `gate ci`'s `ac-coverage` fails while baselined failures no longer fail (the baseline only shrinks). A plain `git commit` fails `sdlc/approval`, which needs `Sdlc-*` trailers on every non-merge commit. Prune one branch at a time: two prunes edit neighbouring lines of `sdlc-baseline.json` and conflict.
- Worktrees: never move `main` with `git update-ref refs/heads/main ...` from a worktree. `main` is checked out in the main checkout, so its index and files go stale and look like uncommitted changes. Fetch and use `origin/main` instead.
- Prove AC tests by mutation: revert each changed path or branch one at a time and confirm a tagged test fails (`ac-red` does this for the build's files).
